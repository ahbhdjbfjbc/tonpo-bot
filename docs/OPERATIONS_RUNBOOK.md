# Operations Runbook — Safe Development

## التشغيل المحلي

1. استخدم Python 3.12.
2. انسخ `.env.example` إلى `.env` واستبدل placeholders محليًا فقط.
3. شغّل PostgreSQL 16 وRedis 7.
4. نفّذ `make migrate` على قاعدة غير إنتاجية.
5. تحقق من `TRADING_DRY_RUN=true`.
6. شغّل البوت عبر `make run` والويب عبر `python -m web.run` عند الحاجة.

## Compose

`docker-compose.yml` يستخدم PostgreSQL 16 وRedis 7. كلمة `POSTGRES_PASSWORD` مطلوبة. الخدمات تتصل بـ `postgres` داخليًا، ولا ينبغي نشر قاعدة البيانات أو MetaDocker للعامة.

### ثوابت النشر

- شغّل `tonpo-migrate` مرة واحدة بنجاح قبل استقبال المرور. Compose يفرض ذلك على البوت والويب؛ في Kubernetes/منصة أخرى شغّل Job واحدًا للمهاجرات وانتظر نجاحه قبل التوجيه.
- مصدر التفويض الإداري الوحيد حاليًا هو `ADMIN_USER_IDS`. أدوار `AdminRole` المخزنة في قاعدة البيانات لا تمنح وصولًا في Telegram أو الويب أو مراجعة الدفع حتى اعتماد خريطة صلاحيات واختبارها لاحقًا؛ أي معرف غير موجود في allowlist يُرفض افتراضيًا.
- شغّل **نسخة واحدة فقط من `tonpo-bot`**. `DBPersistence` يحتفظ بصورة حالة داخل ذاكرة العملية، ويأخذ قفل PostgreSQL advisory lock يمنع تشغيل عملية بوت ثانية على قاعدة البيانات نفسها. توسيع replicas للبوت غير مدعوم حتى نقل حالة المحادثات إلى مخزن موزع ذي تحديثات ذرية. يمكن توسيع web replicas فقط بعد تهيئة reverse proxy وRedis والجلسات ومراجعة إعداداتهم.
- `daily_trades` محجوز بتحديث ذري عند إنشاء intent. الحجز يبقى مستهلكًا عند نتيجة `UNKNOWN` أو `partial` أو أمر معلّق مقبول أو انهيار العملية؛ حرّره النظام فقط عند رفض وسيط صريح أو فشل مؤكد قبل إرسال order. `total_trades` و`total_volume` لا يزيدان إلا بعد تحقق تنفيذ مكتمل. لا تعاود إرسال `UNKNOWN` تلقائيًا.
- Celery queue غير مفعّلة في المنتج: handlers الخاصة بالتنبيه/التقرير/الاتصالات والأسعار غير مكتملة ولا يوجد worker/beat في Compose. لا تعتمد عليها ولا تضبطها يدويًا؛ إرسال المهام يفشل صراحة بدل إسقاطها بصمت. مهام PTB/async المحلية ليست بديلًا عن queue موزعة.
- استراتيجية الترحيل forward-only للإنتاج: راجع migration ثم جرّب `alembic upgrade head` على نسخة staging حديثة من بيانات الإنتاج، وخذ backup مشفرًا قابلًا للاستعادة قبل تغيير الإنتاج. migrations `012` (مسح كلمات مرور MT5 القديمة)، `013` (حقول gateway قد تصبح NULL)، و`015` (بيانات التدقيق/الدعم) ترفض downgrade صراحة؛ لا تحاول تجاوز هذا الحاجز أو استعادة فوق قاعدة الإنتاج. استخدم forward-fix لإصلاح التطبيق/المخطط، أو blue/green إلى نسخة قاعدة مستعادة ومتحقق منها مع تحويل مرور مخطط. لا يُستخدم downgrade إلا لمهاجرة ثبتت عكوسيتها واختبرت على نسخة معزولة.

### مراجعة الدفع اليدوية

- المستخدم ينشئ طلبًا بعنوان المحفظة والمبلغ/الشبكة المحددة ثم يرسل hash وإثبات التحويل؛ يتحول الطلب إلى `submitted` فقط، ولا يمنح ذلك اشتراكًا.
- قائمة المراجعة تتطلب admin عبر allowlist `ADMIN_USER_IDS`: `GET /api/admin/payment-requests?status=submitted`. بعد التحقق الخارجي من المعاملة والمستلم والمبلغ، استخدم `POST /api/admin/payment-requests/{payment_id}/approve` أو `.../reject` مع سبب رفض. الموافقة/الرفض تُسجل في `AdminAuditLog`، والموافقة فقط هي التي تفعل الاشتراك. hash أو webhook غير موثوق لا يفعل الاشتراك.
- لا توجد حاليًا خدمة تحقق on-chain أو مزامنة webhook موثوقة. يجب على المراجع فحص المعاملة على شبكة البلوكشين الصحيحة قبل الموافقة؛ عند عدم القدرة على التحقق، ارفض أو اتركها معلقة للتصعيد ولا تعتمد على إدخال المستخدم وحده.

### نسخ احتياطي واستعادة

يتضمن المستودع أدوات تشغيل لمرة واحدة، لكنه **لا ينشئ جدولة أو تخزينًا خارج المضيف تلقائيًا**. لا تعتبر مجرد وجود volume في Compose نسخة احتياطية.

1. عيّن RPO/RTO والاحتفاظ التشغيلي، وثبّت أدوات PostgreSQL client وGnuPG على مضيف النسخ.
2. أنشئ ملف passphrase عشوائيًا قويًا على secret volume خارج المستودع، بملكية خدمة النسخ وصلاحيات `0600`. استخدم مفتاحًا مستقلًا عن `ENCRYPTION_KEY`.
3. شغّل `DATABASE_URL=... BACKUP_PASSPHRASE_FILE=/secure/path/backup.pass BACKUP_DIR=/secure/local/path ./scripts/backup_postgres.sh`. ينشئ السكربت ملف libpq مؤقتًا بصلاحية `0600` ويحذف URL من بيئة `pg_dump`؛ لا تضع عنوان الاتصال أو passphrase في command arguments أو logs. الأداة تنتج `*.dump.gpg` وملف SHA-256؛ انقل **كليهما** إلى تخزين مقيد خارج المضيف عبر منصة تشغيل معتمدة، وأنشئ الجدولة هناك بعد مراجعة secrets والاحتفاظ.
4. لاختبار الاستعادة، جهّز قاعدة PostgreSQL جديدة ومعزولة وفارغة، واستخدم `RESTORE_DATABASE_URL=... BACKUP_PASSPHRASE_FILE=/secure/path/backup.pass ./scripts/restore_postgres.sh /offhost/tonpo-....dump.gpg`. الأداة تتحقق من SHA-256 وترفض أي قاعدة تحتوي كائنات مستخدم؛ لا تستخدمها على قاعدة الإنتاج، ولا تضع `--clean` أو `--create`.
5. افحص `alembic current`، وأعداد الصفوف الأساسية وسجلات التطبيق، ثم نفّذ smoke tests. وثّق وقت النسخة والاستعادة وRPO/RTO والنتيجة. لا تفتح المرور قبل اعتماد هذا الاختبار.

لا يوجد في هذا المستودع مزود تخزين خارجي أو جدولة backup مُدارة أو اختبار restore على PostgreSQL فعلي؛ يجب إكمالها في بيئة التشغيل قبل إعلان الجاهزية الإنتاجية. لا تستعد فوق قاعدة الإنتاج القائمة.

## التعافي

عند توقف Gateway/Engine أو timeout في أمر: لا تعاود الإرسال تلقائيًا. سجّل `UNKNOWN`، افحص history/positions، ثم نفّذ reconciliation. لا تحذف بيانات الحالة قبل حفظ نسخة واستكمال التحقيق.

## MetaDocker المستقبلي

ابدأ بـ `BRIDGE_READ_ONLY=1`، `METADOCKER_REQUIRE_HTTPS=true`، و`METADOCKER_ALLOWED_HOSTS` بقائمة دقيقة من أسماء/عناوين المحركات؛ لا يكفي اعتبار كل private/loopback/link-local وجهة موثوقة. امنع egress إلى metadata services، استخدم volume دائم وحساب Demo، وشغّل مثيلًا منفصلًا لكل حساب حتى يثبت تصميم provisioning وعزل البيانات.

## غير متاح حاليًا

لا توجد تعليمات تشغيل فعلية لـ MetaDocker داخل البيئة الحالية لأن Engine وMT5 وDemo account غير متوفرين.

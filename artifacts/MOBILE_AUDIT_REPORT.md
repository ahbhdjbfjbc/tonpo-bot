# تقرير فحص مستودع `tonpo-bot`

**المستودع:** `https://github.com/ahbhdjbfjbc/tonpo-bot.git`  
**نطاق الفحص:** نسخة Git سطحية من الفرع `main`، قراءة كاملة للملفات المصدرية والإعدادات والاختبارات والوثائق، دون تعديل المستودع البعيد.  
**تاريخ الفحص:** 2026-10-10  
**حالة التطبيق الجوال:** لم يُنشأ بعد؛ تهيئة Manus-managed Mobile متوقفة لأن Manus Cloud غير متاح في البيئة الحالية.

## الملخص التنفيذي

المشروع عبارة عن بوت Telegram للتداول الآلي عبر MetaTrader 5، مع FastAPI/Web UI، PostgreSQL، Redis، Tonpo SDK، إدارة مخاطر، اشتراكات ومدفوعات، TradingView webhooks، واختبارات واسعة.

- **نقاط جيدة:** 149 ملف Python تقريبًا، 35 وحدة اختبار، 22 migration، حاجز `TRADING_DRY_RUN=true`، مسار fail-closed عند غياب قيود الرموز، وحماية متعددة الطبقات في مسار الإشارات.
- **نجح:** فحص الصياغة بواسطة `python3 -m compileall -q .`، مع تحذير SyntaxWarning واحد في ملف مساعد خارج الحزمة الأساسية.
- **تعذر التحقق:** `pytest` و`ruff` و`mypy` غير مثبتة في بيئة الفحص؛ لذلك لا يجوز اعتبار نتيجة الاختبارات الحالية مؤكدة من هذه الجلسة.
- **أكبر مانع وظيفي:** لا يوجد Gateway حقيقي أو Bridge/EA أو MT5 أو حساب وسيط تجريبي موثق داخل المستودع، ولذلك لا يمكن إثبات تنفيذ صفقة خارجية.
- **أكبر مشكلات التسليم:** اختلاف إصدارات Python/PostgreSQL بين الوثائق وDocker، وعدم اتساق `pyproject.toml` مع `requirements.txt`، وإدراج أرشيف نسخ احتياطي وملفات غير نظيفة داخل Git.

## الأدلة التي جرى فحصها

- بنية المستودع كاملة تقريبًا، بما في ذلك `bot/`, `config/`, `core/`, `database/`, `gateway_client/`, `services/`, `utils/`, `web/`, `tests/`, `artifacts/`.
- `README.md`, `.env.example`, `pyproject.toml`, `requirements.txt`, `requirements-dev.txt`, `Dockerfile`, `docker-compose.yml`, `Makefile`, `TONPO_STATUS.md`.
- وحدات الاختبار الـ35، migrations، مسارات FastAPI، ومكونات Gateway/التنفيذ.
- Git history: commit واحد فقط في النسخة السطحية: `f3cf5cf Full backup to move to GitHub`.

## النتائج المصنفة

### حرجة — P0

#### 1. لا توجد بنية تنفيذ MT5 خارجية قابلة للتحقق

**الدليل:** `TONPO_STATUS.md` يذكر غياب Gateway runtime وTonpo Bridge وMQL5 EA وMT5 وحساب demo، كما أن المستودع يحتوي على عميل Python فقط ولا يحتوي على Gateway أو DLL أو EA أو حزمة Windows.

**الأثر:** لا يمكن إثبات صحة دورة التنفيذ الحقيقية أو المصالحة بعد نتيجة غير معروفة. لا ينبغي تفعيل التداول الحقيقي.

**الإصلاح:** الحصول على حزمة Gateway/Bridge/EA الرسمية من مزود Tonpo، إعداد Windows/MT5 وحساب demo، ثم تنفيذ اختبارات health وsymbol metadata وrejection وreconciliation مع بقاء `TRADING_DRY_RUN=true`.

### عالية — P1

#### 2. الاختبارات الآلية غير قابلة للتشغيل في بيئة الفحص الحالية

**الدليل:** الأمر `pytest -q --disable-warnings` انتهى بـ `pytest: command not found`. كما أن `ruff` و`mypy` غير مثبتين.

**الأثر:** لا توجد نتيجة حديثة قابلة لإعادة الإنتاج من هذه الجلسة، رغم أن `TONPO_STATUS.md` يسجل نجاحًا سابقًا.

**الإصلاح:** إنشاء بيئة افتراضية نظيفة، تنفيذ `pip install -r requirements-dev.txt`، ثم تشغيل `pytest`, `coverage`, `ruff/flake8`, و`mypy` في CI. يجب تسجيل الإصدارات والنتائج كـ artifacts.

#### 3. اختلاف إصدار PostgreSQL بين وثائق المشروع وDocker

**الدليل:** `README.md` يطلب PostgreSQL 16، بينما `docker-compose.yml` يستخدم `postgres:15-alpine`.

**الأثر:** اختلاف سلوك SQL أو أنواع البيانات أو المهاجرات بين بيئة التطوير والإنتاج.

**الإصلاح:** اعتماد إصدار واحد موثق. الأفضل تحديث Compose إلى PostgreSQL 16 بعد اختبار المهاجرات، أو تعديل الوثائق إذا كان الإصدار 15 مقصودًا.

#### 4. اختلاف Python بين الوثائق وDocker وبيانات الحزمة

**الدليل:** README يطلب Python 3.12+، Dockerfile يستخدم Python 3.11، و`pyproject.toml` يعلن `requires-python >=3.10`.

**الأثر:** اختلاف سلوك الاعتماديات والـ typing والـ runtime، خصوصًا مع حزم حديثة.

**الإصلاح:** تحديد مصفوفة دعم رسمية واحدة، ثم جعل README وDocker و`pyproject.toml` وCI متطابقة.

### متوسطة — P2

#### 5. عدم اتساق مصادر الاعتماديات

**الدليل:** `pyproject.toml` و`requirements.txt` لا يعلنان نفس الحزم أو القيود. مثال: `python-jose`, `passlib`, `email-validator`, `phonenumbers`, `sentry-sdk`, `prometheus-client`, `apscheduler`, `slowapi`, `uvicorn` موجودة في requirements ولا تظهر كلها في pyproject. وبالعكس، بعض قيود pyproject مختلفة.

**الأثر:** التثبيت عبر `pip install -e .` قد لا ينتج نفس بيئة `pip install -r requirements.txt`.

**الإصلاح:** اختيار مصدر واحد للحزم (يفضل `pyproject.toml` مع lockfile)، أو إضافة اختبار CI يقارن بيئتي التثبيت ويمنع الانحراف.

#### 6. إعداد coverage يشير إلى مصدر غير موجود أو غير مطابق

**الدليل:** `pyproject.toml` يضبط `source = ["fx_signal_copier"]`، بينما البنية الفعلية تستخدم مجلدات مثل `bot`, `config`, `core`, `database`, `services`, `web` ولا يظهر package باسم `fx_signal_copier`.

**الأثر:** تقارير التغطية قد تكون فارغة أو مضللة.

**الإصلاح:** ضبط `coverage.run.source` على الحزم الفعلية أو استخدام package موحد فعليًا، ثم فرض حد تغطية مناسب بعد التحقق.

#### 7. Docker وCompose لا يفرضان تحققًا مبكرًا كافيًا من الأسرار

**الدليل:** `docker-compose.yml` يسمح بتمرير قيم فارغة، و`.env.example` يحتوي على placeholders للمحافظ ومفاتيح API. لا يظهر في Compose فحص preflight يمنع تشغيل خدمة تداول بإعدادات غير صالحة.

**الأثر:** فشل متأخر أو تشغيل جزئي مربك، مع احتمال سوء تهيئة المدفوعات أو التكاملات.

**الإصلاح:** إضافة أمر preflight آمن يرفض القيم الافتراضية والناقصة، مع رسائل واضحة، مع الإبقاء على `TRADING_DRY_RUN=true` كقيمة افتراضية غير قابلة للتجاوز العرضي.

#### 8. توثيق النشر لا يطابق المستودع الحالي بالكامل

**الدليل:** README يشير إلى مستودع ومؤلفين مختلفين (`KAPKEPOT/tonpo-bot`) بينما المستودع المفحوص هو `ahbhdjbfjbc/tonpo-bot`. كما أن اسم الحزمة `fx-signal-copier` لا يطابق اسم المنتج Tonpo Bot.

**الأثر:** ارتباك في التثبيت والدعم والروابط وعمليات الإصدار.

**الإصلاح:** توحيد اسم المنتج، روابط GitHub، اسم الحزمة، metadata، وأوامر clone/service.

### منخفضة — P3

#### 9. ملفات غير نظيفة أو زائدة داخل Git

**الدليل:** الملفات المتتبعة تتضمن `tonpo_full_backup.tar.gz` بحجم يقارب 2.4MB، و`bot/main_backup.py`، ومسارًا غير معتاد `~/ai_report.py`. كما ظهرت ملفات `__pycache__` في شجرة العمل بعد الفحص بسبب compileall.

**الأثر:** تضخيم المستودع، زيادة سطح التسريب، وتشويش المصدر المعتمد.

**الإصلاح:** إزالة الأرشيفات والنسخ الاحتياطية والملفات المولدة من Git، تحديث `.gitignore`، واستخدام Releases أو تخزين نسخ احتياطية منفصلًا.

#### 10. لا يظهر CI workflow في النسخة المفحوصة

**الدليل:** لم يظهر مجلد `.github/workflows` ضمن بنية المستودع المفحوصة.

**الأثر:** لا يوجد حاجز آلي واضح يمنع دمج كود لا يمر بالاختبارات أو lint أو migration checks.

**الإصلاح:** إضافة CI يشغل compileall، الاختبارات، التغطية، lint، type check، فحص الأسرار، و`alembic check` على الإصدارات المدعومة.

#### 11. تحذير صياغة في ملف مساعد غير قياسي

**الدليل:** `python3 -m compileall -q .` أصدر `SyntaxWarning: invalid escape sequence '\~'` في `~/ai_report.py`.

**الأثر:** ليس عطلًا في المسار الرئيسي، لكنه مؤشر على ملف غير نظيف أو غير مطلوب داخل المستودع.

**الإصلاح:** إزالة الملف إن لم يكن جزءًا من المنتج، أو إصلاح النص الخام/escape ثم إضافته إلى CI.

## ما تم التحقق منه بنجاح

- `git status --short`: لا توجد تعديلات محلية قبل الفحص.
- `python3 -m compileall -q .`: نجح، مع التحذير المذكور أعلاه.
- وجود 35 وحدة اختبار و22 migration تقريبًا.
- وجود حاجز `TRADING_DRY_RUN=true` في الإعدادات والـ Compose والاختبارات.
- وجود مسار fail-closed عند غياب قيود الرموز وفق حالة المشروع.
- وجود اختبارات للأمان، CORS، auth، webhooks، المخاطر، dry-run، websocket، والمدفوعات.

## ما لم يمكن التحقق منه

- نتيجة `pytest` الحديثة بسبب عدم تثبيت pytest في البيئة الحالية.
- جودة lint وtype checking بسبب عدم تثبيت `ruff`/`mypy`.
- اتصال PostgreSQL/Redis الحقيقي.
- اتصال Tonpo Gateway أو تنفيذ صفقة demo.
- دورة Telegram/TradingView خارجية.
- بناء Docker فعلي أو تشغيل migrations على قاعدة حقيقية.
- ميزات native في تطبيق الجوال؛ لم يبدأ تطبيق الجوال لأن Manus Cloud غير متاح.

## خطة الإصلاح المقترحة

### المرحلة 0 — تجهيز قابلية الفحص

1. تفعيل Manus Cloud أو توفير بيئة Cloud لهذه الجلسة حتى يمكن إنشاء تطبيق الجوال المُدار.
2. تثبيت الاعتماديات التطويرية في بيئة معزولة وتسجيل الإصدارات.
3. إضافة CI أولي يمنع الدمج عند فشل compile/test/lint/type check.

### المرحلة 1 — توحيد البناء والتكوين

1. توحيد Python وPostgreSQL في README وDocker وpyproject وCI.
2. دمج مصادر الاعتماديات وإضافة lockfile.
3. إصلاح coverage source.
4. إضافة preflight للإعدادات والأسرار والقيم placeholder.
5. إزالة الأرشيفات والنسخ الاحتياطية والملفات المولدة.

### المرحلة 2 — اختبار التطبيق دون تداول حقيقي

1. تشغيل PostgreSQL وRedis مع migrations نظيفة.
2. تشغيل اختبارات الوحدة والتكامل مع بيانات dummy.
3. اختبار FastAPI وWebSocket وTradingView باستخدام أسرار اختبارية فقط.
4. اختبار idempotency، rate limits، auth، ownership، kill switch، وdry-run.
5. إبقاء `TRADING_DRY_RUN=true` وعدم استخدام حساب live.

### المرحلة 3 — اعتماد Gateway/MT5 التجريبي

1. الحصول على Gateway/Bridge/EA الرسمي من المزود.
2. إعداد Windows VPS وحساب وسيط demo فقط.
3. التحقق من health وsymbol metadata ورفض الأوامر غير الصالحة.
4. اختبار unknown-result reconciliation وعدم تكرار الأوامر.
5. توثيق نتائج الاعتماد قبل التفكير في أي تفعيل حقيقي.

### المرحلة 4 — تطبيق الجوال

بعد توفر Manus Cloud، سيُبنى تطبيق Expo/React Native/TypeScript يعرض:

- ملخص الحالة والأولوية.
- قائمة الأخطاء والنواقص مع مرشحات P0/P1/P2/P3.
- شاشة تفاصيل لكل نتيجة مع الملف والدليل والأثر والإصلاح.
- خطة الإصلاح بمراحل وحالة إنجاز.
- شاشة حدود الفحص وما لم يتم التحقق منه.
- رابط المستودع ومعلومات آخر فحص.
